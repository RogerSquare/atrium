# Redesign intake — List view (ui-list-redesign-001)

Requestor brief, verbatim intent: the current list "does not seem very
friendly to use … would not expect it to work for any new users. Redo the
layout and keep it nice and simple to make it very streamlined to use and
manage tasks; maybe do some grouping as well so that you can follow a thread
of work."

Board reality measured 2026-08-03 (784 active tasks): **659 are done (84%)**,
13 todo, 6 in_progress, 104 review. `parent_task` set on 238 (30%) forming 76
families; `depends_on` non-empty on 186 (24%) — **up from 0% when
`lib/listColumns.js:20` was written; that comment is now stale**; component
74%; phase tags 18%. The single biggest new-user problem is not a missing
feature: it is that the default view is an ungrouped, priority-sorted wall of
mostly-done rows behind a 900px-min-width table.

### Distilled palette

Atrium already ships a complete token system (Apple-ish `--text-*`/`--fill-*`/
`--accent-app` vars + OLED theme); **color tokens are NOT up for grabs in this
redesign — layout, hierarchy, and interaction language are.** Distilled
direction:

- **Row anatomy**: one focal element per row — title high-contrast, everything else muted `[best-guess: linear screenshots]`; priority as a compact left glyph/stripe, metadata trailing right
- **Grouping**: group by Status by default `[token: linear docs]`; per-group collapse with icon + name + count headers; "show empty groups" is a toggle, not a default
- **Sorting**: a table is never unsorted `[token: primer.style]`; sort is a view-level control, supports a secondary layer (Priority, then Updated) `[token: linear docs]`
- **Density**: single-line rows ~36-44px `[best-guess]`; Primer-style density tiers optional, not required for v1 `[token: primer.style]`
- **Row actions**: at most ONE pulled-out visible action per row; the rest live in the detail pane `[token: primer.style]`
- **Typography/spacing/motion**: keep Atrium's existing tokens (`--text-subhead` titles, `--text-caption*` metadata, `--duration-fast` transitions) — no new type scale

### Implicit affordances flagged

| Concern | Detail | Decision |
| --- | --- | --- |
| No keyboard navigation | No ↑/↓ row focus, no Enter-to-open, no Esc-to-close; the table is mouse-only, which contradicts "streamlined to manage tasks". | add |
| No `/` or Cmd+F search focus | The global search box exists in FilterBar but nothing binds a key to focus it from the list. | add |
| Mixed control vocabularies | One toolbar mixes a native `<select>` (group-by), pill buttons (Expand all), and a custom menu (Columns); rows mix native selects with custom chips. Three eras of controls read as unfinished. | add |
| No loading state | Table renders empty (indistinguishable from zero tasks) until the first fetch resolves; Board has no skeleton either but its columns make loading visually obvious. | add |
| No true zero-state CTA | Board's empty state explains the lifecycle and offers "create a task"; List's empty state is one italic line with no action. | add |
| Unlabeled controls | Group-by select, inline status/priority selects, and select-all checkbox lack aria-labels; headers lack aria-sort. TaskRow's disclosure triangle IS labeled — peers are behind. | add |
| No shift-click range select | Board receives `onShiftSelect` (AppShell.jsx:478) but ListView is not passed it and never implements range selection — bulk work in the list is click-per-row. | add |
| Done-dominated default | 84% of rows are done tasks; default sort is priority with no grouping, so the first screen a new user sees is finished work. | add |

## Research findings beyond the contract

1. **The capability/perception gap is the headline.** Almost everything the
   requestor asked for already exists: five flat groupings, a real
   parent/subtask tree with orphan handling (`lib/taskTree.js`), a column
   picker, virtualization, inline editing. It reads as unfriendly because the
   defaults hide all of it: grouping defaults to `none`, the tree mode is the
   seventh option in an unlabeled native select, and 84% of rows are done
   tasks. A layout that surfaces the right defaults matters more than new
   machinery.
2. **"Thread of work" maps to two real structures**: `parent_task` families
   (30% coverage, 76 families, tree already shipped) and the
   research→plan→implement pipeline (`depends_on`, now 24% coverage and
   growing since the continuation endpoint populates it; phase tags on 18%).
   A "Thread" grouping can union both: family trees where they exist,
   phase-chains stitched via depends_on where they don't.
3. **Stale assumption found**: `lib/listColumns.js:18-20` justifies omitting a
   depends_on column because it was "empty on all 769 tasks" — now 24%
   non-empty. Worth revisiting in the plan (not necessarily as a column; as
   thread stitching).
4. **State seams that must not break**: ListView receives already-filtered
   `filteredTasks` from AppShell via FocalZone (AppShell.jsx:463-465) — the
   list must never re-filter; selection state (`bulkSelectMode`,
   `selectedTaskIds`, BulkActionBar as `topSlot`) is owned by AppShell
   (AppShell.jsx:475-500); localStorage keys in play:
   `taskBoardListSort/Dir/Group/Columns`.
5. **Mobile**: the table is `min-w-[900px]` + horizontal scroll
   (ListView.jsx:258) — below MOBILE_BREAKPOINT=768 it's a sideways-scrolling
   spreadsheet. The mobile tab bar cycles into this view
   (mobile-appshell.spec.js).
6. **e2e surface**: only `detail-pane-resize.spec.js` and
   `mobile-appshell.spec.js` touch the list today (plus `task-row-title`
   testid used by both). A rework needs its own spec; existing coverage is
   thin, which lowers regression detection — hence this contract.

## Open questions for the requestor (starred = recommended default)

- **Q1 — Default state for first open?** ★ Group by **Status** with the Done
  group **collapsed** by default (persisted once the user changes it). The
  alternative (keep `none`) preserves today's behavior but keeps the wall of
  done rows.
- **Q2 — What is a "thread"?** ★ A new **Thread** grouping that unions
  parent_task families with research→plan→implement chains stitched via
  depends_on, replacing the current "Parent / subtasks" option. Alternative:
  keep parent-only tree and add a separate phase-chain rollup later.
- **Q3 — Column diet for the default set?** ★ Trim DEFAULT_VISIBLE from 8 to
  6: demote the **ID pill into the title cell** (small mono subtext, still
  copyable) and drop **PR** + **Phase** from defaults (both remain in the
  picker; PR state stays visible via the ID dot → merged into title cell
  metadata). Alternative: keep all 8.
- **Q4 — Control vocabulary?** ★ Replace the three native `<select>`s with
  the app's shared components (segmented/menu), add ↑/↓ + Enter keyboard
  navigation and shift-click range select. Alternative: visual-only reskin.
- **Q5 — Mobile list?** ★ Below 768px render rows as compact cards (title +
  status + priority) instead of the 900px table. Alternative: keep horizontal
  scroll.
